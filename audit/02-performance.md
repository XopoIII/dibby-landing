# Аудит веб-производительности — dibby landing

Статический анализ (по коду, без запуска браузера). Цель: LCP / CLS / INP в зелёной зоне на мобильных.

Анализируемые файлы: `landing/index.html`, `landing/styles.css`, `landing/i18n.js`, `build.cjs`, `dist/index.html` (запечённый EN), воркер `worker.js` + `wrangler.jsonc`.

Файл `index.wasm` (37 МБ в корне) — отдельная игра, в анализ веса лендинга НЕ входит.

---

## Сводка состояния

Базовая гигиена сделана хорошо:
- Шрифты self-host (woff2), preload, `font-display: swap`.
- LCP-картинка (hero) предзагружена как webp с `fetchpriority="high"`.
- У `<img>` проставлены `width/height`, у фреймов телефона/скриншотов — `aspect-ratio`.
- `loading="lazy"` на below-the-fold скриншотах.
- WebP-варианты для всех тяжёлых скриншотов через `<picture>`.
- Скрипты в конце `<body>` (не блокируют первый рендер парсингом).

Основные потери — в трёх местах: **render-blocking CSS без инлайна критики**, **119 КБ i18n.js со всеми 19 локалями ради одной**, и **CLS от JS-инъекции блоков без зарезервированной высоты** (магазины, сетка друзей на 36 ячеек, FAQ, конфетти).

---

## Проблемы по влиянию (отсортировано)

### 1. [CLS — ВЫСОКОЕ] JS-инъекция крупных блоков без зарезервированного места

`landing/index.html` (boot-скрипт) и `i18n.js` строят контент уже после загрузки/парсинга 119 КБ JS. В запечённом `dist/index.html` этих блоков ещё нет (проверено: `.store` = 3 из футера, `.friend` = 1, `.faq-item` = 1 — остальное вставляет JS).

Пустые контейнеры, которые JS наполняет «с нуля», БЕЗ зарезервированной высоты в CSS:
- `[data-stores]` — ряд бейджей магазинов (до 6 штук, в hero и в финальном CTA). `.stores` имеет только `display:flex; gap` — высота 0 до вставки.
- `[data-friends]` — сетка из **36 карточек друзей** (самый большой сдвиг: целый экран контента появляется разом).
- `[data-faq]` — список FAQ (5 элементов).
- `[data-confetti]`, `[data-confetti2]` — ряды картинок.

Когда JS отрабатывает, эти блоки «распухают» от 0 до полной высоты и толкают весь контент ниже вниз → большой CLS, особенно на мобильном, где всё в одну колонку.

**Фикс:**
- Запечь эти блоки в HTML на этапе `build.cjs` (как уже сделано для текста через `data-i18n`), чтобы JS только дополнял/перевешивал ссылки, а не создавал DOM. Это лучший вариант: убирает и CLS, и зависимость рендера от 119 КБ JS.
- Если запекать нельзя — задать контейнерам `min-height` под финальный размер: `.stores { min-height: … }`, `.friends-grid { min-height: … }` (можно через `aspect-ratio`/число рядов), `.faq-list`, `.confetti-row`.
- `friend__pic { height: 74px }` уже задан — но сама сетка появляется целиком, поэтому резерв нужен на уровне `.friends-grid`.

---

### 2. [LCP+CLS — ВЫСОКОЕ] Render-blocking CSS без инлайна критического

`<link rel="stylesheet" href="styles.css">` в `<head>` — единственный внешний, **блокирующий** CSS (31 КБ, ~7.8 КБ gzip). Браузер не рисует ничего, пока не скачает и не распарсит его. На мобильном 3G/4G это +1 RTT к FCP и, как следствие, к LCP (hero-картинка не покажется раньше первого рендера).

Дополнительно: пока CSS не загружен, у hero нет grid-раскладки и `aspect-ratio` фрейма телефона → возможен сдвиг при применении стилей.

**Фикс:**
- Заинлайнить критический CSS (above-the-fold: `body`/фон, `.site-header`, `.hero`, `.phone*`, типографика H1) прямо в `<head>` через `<style>`, а полный `styles.css` грузить неблокирующе:
  `<link rel="preload" href="styles.css" as="style" onload="this.rel='stylesheet'">` + `<noscript>`-фолбэк.
- Минимум — добавить минификацию CSS в `build.cjs` (сейчас `dist/styles.css` побайтово равен исходнику — не минифицируется).

---

### 3. [LCP/INP — ВЫСОКОЕ] i18n.js: 119 КБ (43.8 КБ gzip) со всеми 19 локалями на каждой странице

`landing/i18n.js` (1511 строк) содержит переводы и данные ВСЕХ 19 языков + имена 36 друзей на всех языках. На запечённой `dist/<locale>/` странице нужен ровно ОДИН язык, но грузятся все. Файл подключён `<script src="i18n.js">` **без `defer`/`async`**, и весь видимый интерактив (магазины, друзья, FAQ, конфетти, ссылки CTA) строится только после его загрузки и выполнения boot-скрипта.

Влияние:
- Это +119 КБ передачи и парсинга на главном потоке перед тем, как страница станет «полной» → откладывает момент, когда LCP-зависимый контент и интерактив готовы; крупный парс/исполнение бьёт по INP и TBT на слабых телефонах.
- Один и тот же файл одинаков для всех локалей — но это не помогает первому визиту.

**Фикс:**
- В `build.cjs` генерировать на каждую локаль **узкий** `i18n.<lang>.js`, содержащий только нужный язык (+ имена друзей для него). Сократит payload в ~15–19 раз.
- Добавить `defer` к `<script src="i18n.js">` (сейчас его нет). Сам boot-`<script>` тоже сделать внешним и `defer`, чтобы он не блокировал парсер и выполнялся после i18n.
- Поскольку весь критичный текст уже запечён в HTML (`data-i18n` стоят с реальным текстом), `applyLang()` для текущей локали почти ничего не меняет — основную работу JS (магазины/друзья/FAQ) стоит перенести в билд (см. п.1), тогда JS станет тонким.

---

### 4. [LCP — СРЕДНЕЕ] PNG-фолбэки скриншотов огромны; LCP-картинка тащит лишний PNG в DOM

В `assets/screens/` рядом с webp лежат PNG по 330–540 КБ:
- `menu.png`/`finale.png` — 537 КБ, `gp-earth.png` — 485 КБ, `main.png`/`gp-water.png` — 416 КБ, и т.д.

Для below-the-fold скриншотов это терпимо (`loading="lazy"` + webp в `<picture>` выберется первым на поддерживающих браузерах — почти все). Но:
- **LCP-элемент** — постер телефона в hero: `<picture><source webp><img src="gp-water.png" fetchpriority="high"></picture>`. webp (22 КБ) предзагружен и будет использован, это хорошо. Однако PNG-фолбэк (416 КБ) остаётся в `src` — на браузере без webp (редко) LCP станет очень тяжёлым.
- 416–537 КБ PNG раздувают репозиторий/деплой и риск, если где-то webp не подхватится.

**Фикс:**
- Пережать PNG-фолбэки (они нужны только как фолбэк) или удалить, если webp-покрытие достаточно; как минимум прогнать через `pngquant`/`oxipng`.
- Рассмотреть AVIF для скриншотов (ещё меньше webp) с добавлением второго `<source type="image/avif">`.
- Убедиться, что предзагруженный `gp-water.webp` точно совпадает с тем, что выберет `<picture>` (совпадает — `type="image/webp"`, ок).

### 5. [LCP/CLS — СРЕДНЕЕ] LCP-картинка анимируется (`bob`) и на мобильном уезжает наверх

Фрейм телефона имеет класс `bob` (`@keyframes bob` — `translateY` ±10px, бесконечно). На мобильном (`max-width:880px`) у `.phone-wrap` стоит `order:-1` — картинка становится **первым** крупным элементом экрана, то есть кандидатом в LCP.

- Постоянная transform-анимация LCP-элемента не ломает метрику сама по себе (composited), но создаёт «дёрганье» и тратит кадры. `prefers-reduced-motion` её отключает — для остальных она крутится всегда.
- На мобильном hero-картинка идёт раньше текста, поэтому LCP скорее будет картинка, а не H1 — значит её быстрая доставка критична (см. п.4, preload — уже сделан).

**Фикс:**
- Оставить как есть по приоритету ниже п.1–4, но рассмотреть запуск `bob` только после загрузки (или `will-change: transform` для стабильного композитинга). Это микрооптимизация INP/плавности, не блокер.

---

### 6. [LCP — НИЗКОЕ] Лишний preload второго (декоративного) шрифта

В `<head>` предзагружаются ОБА шрифта:
```
<link rel="preload" href="GolosText.woff2" ...>   (71 КБ — основной текст, body)
<link rel="preload" href="m6x11cyrillic.woff2" ...> (4 КБ — пиксельный, только логотип/eyebrow/числа)
```
m6x11 крошечный (4 КБ), так что вред минимальный, но он конкурирует за пропускную способность с LCP-картинкой и основным шрифтом в самый ранний момент. GolosText (71 КБ) — основной body-шрифт, его preload оправдан.

**Фикс:**
- Оставить preload только для `GolosText.woff2`; m6x11 (4 КБ, декоративный) пусть грузится обычным порядком из CSS — `font-display: swap` уже защищает от невидимого текста. Освободит ранний bandwidth для LCP-картинки.
- (Опционально) сабсеттинг GolosText под латиницу для не-кириллических локалей — но это усложнит билд.

---

### 7. [CLS — НИЗКОЕ] Шрифтовой swap может дать небольшой reflow

`font-display: swap` на GolosText/m6x11 — правильный выбор для FCP, но swap с системного фолбэка на загруженный шрифт может слегка сдвинуть текст (разные метрики). H1 (`text-wrap: balance`) и leды могут переразбиться.

**Фикс (опционально):**
- Добавить `size-adjust`/`ascent-override` в `@font-face`, подогнав метрики фолбэка под GolosText, чтобы swap был «бесшовным». Низкий приоритет — preload уже минимизирует окно swap.

---

### 8. [INP — НИЗКОЕ] Обработчики и таймеры

`i18n.js`/boot — логика лёгкая, но отметить:
- `crossfade()` создаёт `setInterval` каждые 3600 мс, переключая классы на 5 картинках в hero-телефоне — крутится постоянно. Не блокирует, но держит таймер живым. `prefers-reduced-motion` его отключает.
- FAQ-аккордеон считает `a.scrollHeight` при каждом клике (форс reflow) — на 5 пунктах несущественно.
- `document.addEventListener("click", …)` на закрытие меню языка — глобальный, но дешёвый.
- Главная стоимость INP здесь — не обработчики, а первичная сборка DOM из 119 КБ JS (п.3) и сетки 36 друзей (п.1).

**Фикс:** покрывается п.1 и п.3 (тонкий per-locale JS + запечённые блоки).

---

### 9. [Кеширование — СРЕДНЕЕ, пересекается с #3 аудита воркера] Нет явных Cache-Control для статики

`worker.js` обрабатывает только `/` (locale-редирект с `Cache-Control: no-store` — корректно для per-request решения) и для всего остального делает `env.ASSETS.fetch(request)` **без задания заголовков**. То есть Cache-Control для `styles.css`, `i18n.js`, картинок и шрифтов определяется дефолтами Cloudflare Workers Assets.

Workers Assets по умолчанию отдаёт иммутабельные (хешированные) ассеты с длинным кешем, но файлы здесь — **не хешированы** (`styles.css`, `i18n.js`, `assets/screens/*.webp` с фиксированными именами). Для нехешированных имён дефолтный публичный TTL короткий → повторные визиты перекачивают шрифты/CSS/JS/картинки чаще, чем нужно.

**Фикс:**
- В `build.cjs` добавить хеш в имена статики (`styles.[hash].css`, `i18n.[hash].js`, картинки) ИЛИ задать в воркере/`assets` явные `Cache-Control: public, max-age=31536000, immutable` для `/assets/*`, шрифтов и (при версионировании) CSS/JS.
- HTML оставить с коротким TTL/`must-revalidate` (контент меняется).
- Детальнее — в аудите воркера (#3).
